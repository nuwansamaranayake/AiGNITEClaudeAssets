# Folder Layout

One-line summary: What goes where in an AiGNITE mobile project and the reasoning behind each split.

## Top-level tree

```
<project-root>/
├── app/                    # Expo Router screens. File-based routing.
├── components/             # Reusable presentational components.
├── lib/                    # Cross-cutting helpers and singletons.
│   ├── supabase.ts         # Supabase client and RLS query helpers.
│   ├── auth.ts             # Auth state hook and session management.
│   └── theme.ts            # Design tokens, colors, typography.
├── hooks/                  # Custom React hooks. One file per hook.
├── services/               # External integrations.
│   ├── mcp-client.ts       # Calls AiGNITE MCP servers.
│   ├── notifications.ts    # Push notification setup.
│   └── stripe.ts           # Subscription billing.
├── assets/                 # Images, fonts, icons.
├── scripts/                # Dev tooling scripts.
│   └── smoke-test.sh       # Real-endpoint smoke test.
├── .env.local.example      # Documented environment variables.
├── .gitignore
├── app.json                # Expo config.
├── eas.json                # EAS Build profiles.
├── package.json
├── tsconfig.json           # Strict mode on.
├── eslint.config.js        # No em dash rule included.
├── prettier.config.js
├── Makefile                # check, up, smoke targets.
├── CLAUDE.md               # Engineering standards for downstream sessions.
└── API_CONTRACT.md         # Generated by supabase-bootstrap.
```

## Why this split

### `app/` versus `components/`

`app/` holds screens. Each file is a route. Routing logic lives here.

`components/` holds presentational pieces. No routing logic. No business logic that talks to the network. A component renders props and emits events.

Mixing the two produces screens that are hard to test and components that are hard to reuse.

### `lib/` versus `services/`

`lib/` is for code with no external network dependency at runtime once initialized. The Supabase client lives here because the client is a singleton with internal state.

`services/` is for code that wraps an external system. Each service module exports a typed API for one external system.

The split matters at audit time. Security audits scan `services/` for missing input validation and exposed secrets. They scan `lib/` for shared logic that leaks credentials.

### `hooks/`

One hook per file. Named with `use` prefix. Co-located only when the hook is screen-specific and lives in `app/` next to the screen.

Hooks that wrap a `services/` module live in `hooks/`. Example: `hooks/useFloodAlerts.ts` wraps `services/mcp-client.ts`.

### `scripts/`

Dev tooling lives here. The `smoke-test.sh` script is the canonical entry point for real-endpoint verification. The `three-tier-test` skill reads this script to know which endpoints to probe.

## What never goes in this tree

- Generated artifacts. EAS build output stays in `dist/` (gitignored).
- Secrets. Real `.env.local` is gitignored. Only `.env.local.example` is committed.
- Vendor code. Use `node_modules`, not vendored copies.

## When to deviate

These rules are defaults. Deviate when:

- The project has a domain so specialized the standard split obscures the work.
- The team has agreed in writing on a different convention.

Document the deviation in the project `CLAUDE.md` so downstream sessions see it.
